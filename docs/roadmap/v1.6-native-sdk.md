# v1.6 — the native SDK, and one native core

Status: **planned 2026-08-11.** Owner decision: build it, finish it,
ship it as one piece. Sentori already has native code; this does not
add a second implementation beside it — it makes the existing one the
product and turns the React Native package into a consumer of it.

Asked for by insight (2026-08-11): `/apps/insight` and
`/apps/consumer` are Swift + Kotlin with no React Native, and Sentori's
only mobile surface is an npm package. They are blocked, and they
explicitly declined to reimplement the HTTP contract themselves —
correctly, since a second implementation drifts silently and push is
the path where nobody notices.

## What is already true

The native code is not a thin shim around JS. It is 4,225 lines that
already do the hard parts, and it is almost entirely free of the
bridge:

| | lines | files free of the bridge |
|---|---:|---|
| iOS (`sdk/react-native/ios`) | 1,960 | 8 of 9 |
| Android (`sdk/react-native/android`) | 2,265 | 10 of 11 |

Coupling is concentrated in `SentoriModule.swift` (24 references) and
`SentoriModule.kt` (3). The three Android files that appear to
reference React are matching *string literals* —
`"com.facebook.react."` for frame filtering, a drawable class name —
not imports.

So: crash handling, ANR/hang watchdogs, screenshot and wireframe
capture, thread sampling, mobile vitals, and the whole push
implementation are already portable. The bridge is 340 lines.

## What genuinely does not exist

Every line of network code is JavaScript. `URLSession` appears 0 times
in the Swift tree; there is no OkHttp or `HttpURLConnection` in the
Kotlin tree. The native side buffers and the JS side sends.

Ported per platform, that is roughly 700 lines of behaviour:

| JS today | lines | what a native SDK needs it for |
|---|---:|---|
| `sdk/react-native/src/transport.ts` | 312 | batching, retry, offline queue — the only place the SDK talks to the network |
| `sdk/react-native/src/init.ts` | 137 | the single configuration entry point |
| `sdk/core/src/identity.ts` | 112 | SHA-256 identity hashing, client-side, so a raw identity never leaves the device |
| `sdk/react-native/src/scope.ts` | 50 | current user + context patch |
| `sdk/core/src/signal-ring.ts` | 56 | the 60-second ring that gives an error its lead-up |
| `sdk/react-native/src/config.ts` | 46 | runtime config |

This is the actual work. The rest is moving files.

## The shape

```
sdk/native/ios/         Swift Package "Sentori"           ← the core
sdk/native/android/     Maven jp.golia.sentori:sentori    ← the core
sdk/react-native/       the bridge only, depending on both
```

One home for each platform's native code. The React Native package
stops carrying an implementation and starts carrying a binding to one,
which is what "merge them" has to mean if it is to survive the next
change: a copy would let the two drift, and drift in push is invisible
until someone is not notified.

Consequence, stated plainly: an RN release can then require a native
release. Local development and CI resolve the native packages from the
working tree (a path-based pod, a Gradle composite build), so nothing
has to be published to iterate.

## Stages

### S1 — a gate on iOS, before anything moves

`sdk/react-native/ios/Tests/` holds 214 lines of XCTest across three
files. Nothing runs them: `xcodebuild` appears in no workflow, no
script, and no `package.json`. They have never failed because they
have never executed.

That is the platform about to become a published artifact, and the
platform whose code is about to move. The gate comes first, or the
extraction happens with nothing watching.

- A workflow job that builds the Swift package and runs XCTest on a
  macOS runner.
- Red path: break an assertion on purpose, watch it fail, restore.
- Android already has `android-unit` in `mobile-e2e`; extend it to the
  extracted module rather than the RN host project.

### S2 — extract the core, RN keeps working

Move the bridge-free files to `sdk/native/{ios,android}`. Nothing
changes behaviourally; this is the merge.

- `SentoriModule.swift` / `.kt` stay in `sdk/react-native`, and become
  the only files there.
- The podspec depends on the `Sentori` pod; `android/build.gradle`
  depends on the Maven artifact, resolved from the working tree in dev
  and CI.
- Gate: no `.swift` or `.kt` outside `sdk/native` other than the two
  bridge files, so a copy cannot reappear.
- The RN suite (107 tests), `android-unit`, and the new iOS job all
  stay green across the move. If they do not, the move is wrong.

### S3 — the layer that was only ever JavaScript

Transport, config, scope, identity, signal ring — in Swift and in
Kotlin, against `docs/protocol.md`.

The iron rule applies unchanged and is the hard part of this stage:
the verbs never throw, never block the caller, and do O(1) work on the
calling thread. A native SDK has no JS event loop to hide behind, so
"fire and forget" has to be a real queue on a real background thread,
with a bounded buffer and a disk spill that cannot grow without limit.

- Identity hashing must produce byte-identical output to
  `identity.ts` for the same input. A test asserts that against
  fixtures shared with the JS suite — two implementations of one hash
  is exactly the drift insight was worried about, so it gets a gate
  rather than a promise.
- Transport asserts the same wire shape the server's e2e already
  checks, against a real server in `docker compose`, not a mock.

### S4 — the public surface

The eight verbs plus push, in both languages, semantically identical
to the JS surface:

- `init`, `user`, `context`, `error`, `warn`, `trace`, `assert`,
  `probe`, `pushSignal`
- push: permission, token acquisition and rotation, registration with
  `userKey`, foreground and tap callbacks, revoke — the six things
  insight listed
- `register()` returns a result and never throws, matching RN 6.0.0

### S5 — packaging and publication

- iOS: `Package.swift` for SwiftPM; the podspec kept for CocoaPods
  hosts, both from the same sources.
- Android: Maven publication to a public repository, `minSdk 24`,
  `jvmTarget 17`, Firebase `compileOnly` so an app that does not use
  push does not carry it.
- Versions move together with the npm packages, and the existing
  version-constant sync grows a row for each new one.

### S6 — the apps that prove it

A Swift example and a Kotlin example, both built in CI. Not a snippet
in a README: the RN example app is what has caught real breakage —
the SO_REUSEPORT-class problems only show up in a real build.

Docs: `docs/sdk-swift.md` and `docs/sdk-kotlin.md`, plus
`docs/protocol.md` gaining `/v1/push/*`, which it still does not
document.

## What this does not include

- Replay and screenshot capture on the native surface. The code moves
  with everything else and keeps working for React Native, but the
  standalone API does not expose it in v1.6 — it needs an attachment
  upload path that S3 does not build.
- HCM / MiPush. They stay where they are, still untested against real
  credentials.

## The thing to keep checking

Every stage above adds a surface. This repo's most frequent defect,
by a wide margin, is a surface that exists, looks right, and has
nothing watching it — 214 lines of iOS tests nobody runs, a `metadata`
column empty since it was created, three unbalanced INSERTs, a peer
range containing nothing. Each stage lands with its gate, and each
gate gets its red path run before the stage is called done.
