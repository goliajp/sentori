# v1.5 — push becomes part of the product

Status: **planned 2026-08-10**. Owner decision: push is a feature we
want, formally inside v1, with the dashboard and SDK finished, wired
into Sentori's own model rather than living beside it. `expo-compat`
stays.

## Where it stands

Everything below already exists and passes the gates. None of it is
reachable from the dashboard, and the code calls itself "carried;
outside v1 acceptance".

| Piece | State |
|---|---|
| `/v1/push/*` — register / revoke token, subscribe / unsubscribe topic, send, receipt, ack, preferences | 11 routes, working |
| `/v1/push/expo-compat/{send,receipts}` | working — Expo's wire shape in and out |
| `/admin/api/projects/{id}/push/*` — credentials CRUD, test send, sends list, retry, retry-all-failed | 6 routes, working |
| Tables | `push_tokens`, `device_tokens`, `device_topics`, `push_credentials`, `push_sends`, `push_delivery_logs`, `push_preferences` |
| Worker | `push_worker`, 5 s poll, retry + quarantine |
| Providers | APNs, FCM, WebPush, HCM, MiPush |
| RN SDK | `sentori.push.*` — register / unregister / status / requestPermission, 477 lines |
| CLI | `push send` / `push receipt` / `push creds` |
| **Dashboard** | **nothing. `webapp/src/lib/api.ts` has zero push methods** |
| Production | 0 tokens, 0 sends |

A backend API with no dashboard is not shipped
(`feedback_webapp_ux_is_delivery`). That is the gap this plan closes,
and the reason push has no users is most likely that nobody can see it.

## What "integrate into Sentori" means

Push today is a parallel universe: its own identity (`app_user_id`),
its own admin pages that do not exist, its own operational data that
nothing surfaces. The five-kind model, issues, releases, environments
and the triage loop do not know it is there.

Four joins make it Sentori's push rather than a push service that
happens to share a database.

1. **One identity.** `push_tokens.app_user_id` is a free string the
   host sets. Sentori already has `userKey` — the salted identity hash
   every event carries, computed client-side. Register the device
   against the same `userKey`, and the audience of a send becomes
   describable in the terms the rest of the product already uses.
2. **Notify the people it happened to.** With one identity, an issue
   can answer "who hit this" — `issue_user_hits` already stores it —
   and the dashboard can offer *notify the affected users* from the
   issue itself. That is the join no bolted-on push service can make,
   and the reason to have push inside the product at all.
3. **A failed delivery is observability.** A send that fails is
   exactly what this product exists to show. Delivery health belongs
   on the project health card and in the Instruments panel next to
   asserts, probes and traces — not in a log nobody opens.
4. **Release and environment travel with a send.** `push_sends` knows
   neither. Carrying them makes a campaign sliceable the same way
   everything else is: which release, which environment.

## Stages

Each stage ships on its own and leaves the product coherent.

### S1 — the dashboard exists (server + webapp)

- `webapp/src/lib/api.ts`: the six admin push routes typed.
- Settings gains a **Push** tab: credentials per provider with
  configured / validated status, a test send, and the delivery table
  with retry. Empty states that say what to do, like every other tab.
- New `GET /admin/api/projects/{id}/push/health` — 24 h sent / failed /
  queued, failure reasons grouped, quarantined token count. One
  request for the card rather than the dashboard aggregating a list.
- Drop "carried / outside v1 acceptance" from the router, the SDK
  barrel and the design docs.
- e2e: register a token, send, assert the send appears and the
  credential status reads back.

### S2 — one identity

- `POST /v1/push/tokens` accepts `userKey` and stores it alongside
  `app_user_id` (additive; `app_user_id` keeps working — existing
  integrations do not change).
- SDK passes the identity hash it already computes.
- Migration: nullable column, no backfill. A token registered before
  this has no `userKey` and simply is not addressable by issue.

### S3 — notify the affected users

- `POST /admin/api/issues/{id}/notify` — audience is that issue's
  `issue_user_hits` joined to live device tokens; body is a title and
  a message; the send is recorded with the issue id.
- Issue page: a button behind a confirmation that says exactly how
  many devices it will reach, and refuses when that number is zero.
- The issue's activity log records who notified whom and when.

### S4 — delivery is observable

- `push_sends` carries `release` and `environment`.
- Instruments gains a **Push** panel: per-provider 24 h delivery rate,
  the failure reasons behind it, quarantined tokens.
- Project health card gains a delivery line, next to the backend
  availability line it already has.

### S5 — the SDK a new user meets

- `sentori.push.register()` returns a result rather than throwing on a
  denied permission: `{ ok: true, handle }` or
  `{ ok: false, reason: 'permission-denied' | 'no-transport' | … }`.
  A push opt-in that throws inside someone's `useEffect` is the
  failure mode this product's whole contract is written against.
- Delegation to `expo-notifications` when the host has it (above).
- `docs/sdk-react-native.md` documents `sentori.push.*` — it documents
  none of it today — and `docs/protocol.md` documents `/v1/push/*`,
  which it also does not.
- `docs/design/push-architecture.md` reconciled with what shipped.

## The integration ergonomics — how a new user gets push

The owner's ruling: existing integrations are not a constraint; a
**new** user has to find this easy, push is a permanent capability of
the product, and `expo-notifications` compatibility is kept — but as
something *Sentori* uses, not something the integrator has to touch.

Target, end to end:

```
1. app.json      →  plugins: ["@goliapkg/sentori-expo"]
2. dashboard     →  Settings ▸ Push ▸ paste the APNs key / FCM
                    service account, press Test
3. app code      →  await sentori.push.register()
```

Step 1 already works: the config plugin injects the iOS background
mode and `aps-environment` entitlement, the Android
`POST_NOTIFICATIONS` permission, the google-services plugin,
`firebase-messaging`, and copies `google-services.json` at prebuild.

Step 2 **does not exist** — credentials can only be set through an
admin API nobody can see. That is why push has no users, and it is S1.

Step 3 works but throws on a denied permission and is documented
nowhere.

### Sentori uses `expo-notifications`; the integrator does not

Most React Native apps that will adopt this are Expo apps, and many
already have `expo-notifications` installed. Two libraries both
swizzling the iOS `AppDelegate` and both registering an FCM service is
not a style disagreement — it is a lost token or a duplicated tap
callback, and it is the single most likely way this feature breaks in
someone else's app.

So the SDK **detects and delegates** rather than competes:

| Host app has | Token comes from | Permission prompt | Sentori still owns |
|---|---|---|---|
| `expo-notifications` | `getDevicePushTokenAsync()` | its `requestPermissionsAsync()` | server registration, the `ipt_` handle, ack pipeline, delivery, quarantine |
| nothing | Sentori's own native module (already built, both platforms) | our `pushRequestPermission()` | same |

The customer writes `sentori.push.register()` either way and never
imports `expo-notifications` — it is a resolution detail, the way
`AsyncStorage` already is in this SDK. Detection is a guarded dynamic
resolve, never a hard dependency: `expo-notifications` stays an
optional peer, and an app without it pays nothing.

This also settles the client-side shim question. We do **not** rebuild
`@goliapkg/sentori-react-native/expo-compat` — a drop-in replacement
for `expo-notifications`' API surface. That was compatibility for
people migrating off it; the design above is better for the new user
it is aimed at, and this product does not carry facades of other
people's APIs.

`POST /v1/push/expo-compat/send` and its receipt route **stay** —
those are the *server* wire shape, so a backend written against
`expo-server-sdk` can point at Sentori and send. 113 lines of
translation in front of the same pipeline, costing nothing.

## Not in scope

- Campaign scheduling, segmentation beyond "the users on this issue",
  A/B — a notification product, not this.
- HCM / MiPush beyond what already exists; they stay wired and
  untested against real credentials.
